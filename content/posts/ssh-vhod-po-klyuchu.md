У меня дома мини-ПК с Proxmox и тринадцатью контейнерами: DNS, обратный прокси, медиатека, мониторинг. До этой недели ключ стоял только на самом узле, а в контейнерах ключей не было: попасть в них можно было только через узел. Чтобы посмотреть журнал одного сервиса, нужно было сначала войти на узел и уже оттуда зайти в контейнер.

Теперь ключ лежит во всех контейнерах, а вход выглядит так: `ssh media`. Ниже рассказываю, почему ключ надёжнее пароля, как его завести и разложить, и как настроить короткие имена.

## Чем плох пароль

При входе по паролю вы отправляете серверу сам секрет. Из этого следует несколько неприятных вещей.

- Пароль можно подобрать. Серверы с открытым в интернет портом 22 перебирают постоянно, попытки входа видны в журнале `sshd`.
- Пароль получает сервер. Если сервер взломан или вы по ошибке подключились не туда, секрет утёк.
- Пароли повторяются. Один и тот же пароль на пяти машинах означает, что утечка на одной открывает все.
- Пароль приходится вводить. Чем чаще вводишь, тем короче его хочется сделать.

## Как устроен ключ

Ключ состоит из двух половин. Закрытая лежит у вас на компьютере и никуда не передаётся. Открытую вы кладёте на сервер, в файл `~/.ssh/authorized_keys`. Открытая половина не секрет: её можно показывать кому угодно.

При входе сервер не просит прислать секрет. Клиент подписывает закрытым ключом данные, привязанные именно к этому соединению, а сервер проверяет подпись открытым. Подпись одноразовая: перехватив её, в другой сеанс войти нельзя.

Отсюда три свойства, которых нет у пароля.

1. Подбирать нечего. Перебрать ключ Ed25519 за разумное время невозможно.
2. Серверу нечего украсть. Взломав сервер, злоумышленник получит только открытые ключи, а с ними никуда не войти.
3. Доступ отзывается одной строкой. Удалили строку из `authorized_keys`, и этот ключ больше не работает. Остальные ключи и остальные серверы это не затрагивает.

## Создаём ключ

На Mac или в Linux достаточно одной команды:

```bash
ssh-keygen -t ed25519 -C "macbook"
```

Ed25519 сейчас разумный выбор по умолчанию: ключи короткие, работают быстро и поддерживаются любым современным сервером. RSA стоит брать, только если на той стороне очень старая система.

Команда спросит, куда сохранить ключ, и предложит задать парольную фразу. Фразу задайте. Она шифрует закрытый ключ на диске: если ноутбук украдут или файл попадёт в чужую резервную копию, без фразы ключ бесполезен.

Вводить фразу каждый раз не придётся. На Mac её запоминает связка ключей:

```bash
ssh-add --apple-use-keychain ~/.ssh/id_ed25519
```

Чтобы ключ подхватывался сам и после перезагрузки, в начало файла `~/.ssh/config` добавляются две строки. `UseKeychain` есть только на Mac, в Linux клиент на неё выдаст ошибку, там эту строку не пишите:

```
Host *
    AddKeysToAgent yes
    UseKeychain yes
```

В итоге получаются два файла: `id_ed25519` с закрытым ключом и `id_ed25519.pub` с открытым. Первый никому не отправляйте и не копируйте на другие устройства. Для второго ноутбука или телефона заведите отдельный ключ. Тогда потерянное устройство отключается удалением одной строки, а остальные продолжают работать.

## Кладём ключ на сервер

Если на сервер пока можно войти по паролю, всё делает одна команда:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@192.168.0.18
```

Она спросит пароль в последний раз и допишет открытый ключ в `authorized_keys`.

Если входа по паролю нет, ключ добавляется вручную с консоли сервера:

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo 'ssh-ed25519 AAAA... macbook' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

Права важны. Если каталог или файл доступны на запись кому-то кроме владельца, сервер молча откажется принимать ключ.

В контейнерах Proxmox у меня входа по паролю для root не было вовсе, поэтому я раскладывал ключ с узла, одной командой на контейнер:

```bash
cat macbook.pub | pct exec 111 -- sh -c \
  'umask 077; mkdir -p /root/.ssh; cat >> /root/.ssh/authorized_keys'
```

## Сверяем отпечаток при первом входе

При первом подключении клиент спросит, доверять ли серверу, и покажет отпечаток его ключа:

```
ED25519 key fingerprint is SHA256:Xk3v...пример...Qw8
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

Обычно здесь не глядя отвечают `yes`. Делать так не стоит: этот вопрос и есть защита от подмены сервера. Отпечаток нужно сравнить с настоящим, полученным по другому каналу. На сервере, с его консоли, он выводится так:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Если совпало, отвечайте `yes`. Клиент запомнит ключ сервера в `~/.ssh/known_hosts` и больше спрашивать не будет. Если позже вместо входа появится предупреждение о том, что ключ сервера изменился, сначала разберитесь почему. Переустановка системы даёт такое же сообщение, как и чужая машина на этом адресе.

Проверку отпечатков не отключайте. Параметр `StrictHostKeyChecking no` из старых инструкций убирает вопрос вместе с защитой.

## Отключаем вход по паролю

Пока сервер принимает пароль, ключ даёт только удобство. Перебирать пароль по-прежнему можно. Поэтому после проверки входа по ключу пароли стоит запретить. В Debian и Ubuntu для этого создаётся файл `/etc/ssh/sshd_config.d/10-keys-only.conf`:

```
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin prohibit-password
```

Затем проверка настроек и перечитывание:

```bash
sshd -t && systemctl reload ssh
```

Порядок здесь такой, чтобы не запереть себя снаружи:

1. Убедитесь, что вход по ключу работает.
2. Не закрывайте текущий сеанс.
3. После `reload` откройте второй терминал и войдите заново.
4. Только когда второй вход прошёл, закрывайте первый.

На домашнем сервере есть запасной путь через консоль Proxmox или монитор с клавиатурой. На арендованном сервере убедитесь заранее, что у провайдера есть консоль восстановления.

## Короткие имена

Теперь про удобство. Полная команда входа выглядит так:

```bash
ssh -i ~/.ssh/id_ed25519 root@192.168.0.18
```

Адреса тринадцати контейнеров я наизусть не помню. Всё это записывается один раз в файл `~/.ssh/config`:

```
Host pve
    HostName 192.168.0.10

Host media
    HostName 192.168.0.18

Host kuma
    HostName 192.168.0.16

Host pve media kuma
    User root
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
```

После этого работает `ssh media`. Тем же именем пользуются `scp`, `rsync` и `git`, например `rsync -a media:/var/log/ ./logs/`.

Пара пояснений к файлу.

- Файл не должен быть доступен на запись никому, кроме вас, иначе клиент откажется его читать. Проще всего поставить права 600.
- Общие параметры вынесены в последний блок, чтобы не повторять их у каждого имени. Клиент читает файл сверху вниз и для каждого параметра берёт первое найденное значение.
- `IdentitiesOnly yes` заставляет клиент предлагать только указанный ключ. Без этой строки он перебирает все ключи подряд. Сервер по умолчанию даёт шесть попыток, и если ключей больше, соединение обрывается с ошибкой «Too many authentication failures» раньше, чем очередь дойдёт до нужного.

## Чего ключ не решает

Ключ закрывает подбор и кражу пароля, но не всё остальное.

- Закрытый ключ без парольной фразы на украденном ноутбуке даёт готовый вход на все ваши серверы. Фраза и шифрование диска обязательны.
- Если на вашем компьютере вредоносная программа, она воспользуется ключом так же, как вы.
- Пересылка агента (`ForwardAgent yes`) отдаёт серверу возможность входить от вашего имени, пока вы подключены. Включать её стоит только для серверов, которым вы доверяете полностью. Для перехода через промежуточный узел лучше подходит `ProxyJump`.
- Ключ даёт тот доступ, который есть у учётной записи. Ключ для root открывает полный доступ.

Последнее можно сузить. В `authorized_keys` перед ключом пишутся ограничения: `from="192.168.0.0/24"` разрешает вход только из домашней сети, а `command="..."` позволяет ключу выполнить одну заданную команду и больше ничего. У меня так работает мониторинг: его ключ на узле умеет только отдать показания датчиков, оболочку он не получает.

## Итог

Вся настройка сводится к одной команде на создание ключа, по команде на каждый сервер и одному файлу с именами. Взамен пароль перестаёт быть входом на сервер, каждое устройство отключается отдельно, а вход сокращается до `ssh media`.

Если у вас один сервер, начните с ключа и запрета паролей. Если больше одного, сразу заведите `~/.ssh/config`: он окупается в первый же день.

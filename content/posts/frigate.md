![Frigate NVR — система видеонаблюдения с AI](/images/external/frigate-logo.svg "Frigate NVR")


Разворачиваем систему видеонаблюдения Frigate на сервере в Yandex Cloud: записи хранятся на отдельном диске, а к домашним камерам сервер ходит через защищённый VPN NetBird.

По шагам:

* настройку NetBird
* подключение сервера к домашней сети
* подключение и монтирование диска
* установку Docker и Docker Compose
* установку и настройку Frigate
* настройку хранения видео
* получение доступа к Web UI

---

## Архитектура

![Yandex Cloud — облачная платформа](/images/external/yandex-cloud-logo.svg "Yandex Cloud")

Схема работы: камеры отдают RTSP-поток в домашней локальной сети. На домашнем устройстве (роутер, NAS или ПК) стоит NetBird, и оно работает шлюзом (routing peer) в домашнюю подсеть. NetBird соединяет это устройство с виртуальной машиной в Yandex Cloud. Frigate в Docker на VM забирает потоки по локальным адресам камер через этот шлюз, пишет записи на отдельный диск и отдаёт Web UI по HTTPS на порт 8971.

```
Домашние камеры
      │
      │ RTSP
      │
Домашний сервер / роутер (routing peer NetBird)
      │
      │ NetBird VPN
      │
Yandex Cloud VM
      │
      │ Docker
      │
      │ Frigate
      │
      └── /data/frigate/media (записи)
```

## Часть 1. Настройка NetBird

![NetBird — Zero Trust VPN на базе WireGuard](/images/external/netbird-logo.png "NetBird")

NetBird поднимает защищённую приватную сеть между:

* сервером в Yandex Cloud
* домашней сетью

**Зачем это нужно:** Камеры находятся дома, а Frigate — в облаке. Без VPN сервер в Yandex Cloud не сможет достучаться до RTSP-потоков камер в вашей локальной сети. NetBird создаёт зашифрованный туннель между облаком и домом — камеры остаются за NAT, но сервер получает к ним доступ как к устройствам в одной сети. Это безопаснее, чем пробрасывать порты на роутере.

Официальный сайт:

[https://app.netbird.io/](https://app.netbird.io/)

---

## Шаг 1. Регистрация и вход

Перейдите:

[https://app.netbird.io/](https://app.netbird.io/)

Создайте аккаунт или войдите.

**Зачем:** NetBird Cloud управляет всеми подключёнными устройствами и правилами доступа. Без аккаунта вы не сможете создать Setup Key и связать сервер с домашней сетью.

---

## Шаг 2. Создание Setup Key для сервера

Перейдите:

```
Settings → Setup Keys
```

Нажмите:

```
Create Setup Key
```

Укажите:

Name:

```
yandex-cloud
```

Auto-assign groups:

```
remote
```

Сохраните Setup Key.

Пример:

```
6A40F5F1-777-XXXX
```

**Зачем:** Setup Key — это токен для подключения устройства к вашей NetBird-сети (бывает одноразовым и многоразовым, тип выбирается при создании). Он привязывает сервер к группе `remote` и позволяет потом настроить правила: кто к кому может подключаться. Отдельный ключ для облачного сервера нужен, чтобы отличать его от домашних устройств в политиках доступа.

**Важно:** подключайте сервер именно через Setup Key. Устройства, добавленные через интерактивный SSO-вход, по умолчанию раз в 24 часа требуют повторной авторизации и без неё отключаются; на подключённые по Setup Key это не распространяется.

## Шаг 3. Установка NetBird на сервер Yandex Cloud

Подключитесь к серверу:

```bash
ssh skv@SERVER_IP
```

Установите NetBird:

```bash
curl -fsSL https://pkgs.netbird.io/install.sh | sh
```

Подключите сервер:

```bash
sudo netbird up --setup-key YOUR_SETUP_KEY
```

Проверьте статус:

```bash
netbird status
```

Должно быть:

```
Management: Connected
Signal: Connected
```

**Зачем:** NetBird-клиент на сервере подключает его к вашей приватной сети и выдаёт ему виртуальный IP (например, 100.64.0.x). После этого сервер сможет обращаться к домашним устройствам по их NetBird IP, как будто они в одной локальной сети.

---

## Шаг 4. Установка NetBird дома

На домашнем сервере или компьютере:

```bash
curl -fsSL https://pkgs.netbird.io/install.sh | sh
```

```bash
sudo netbird up --setup-key YOUR_HOME_SETUP_KEY
```

Добавьте устройство в группу (проще всего сразу указать её в Auto-assign groups у домашнего Setup Key):

```
Home
```

**Зачем:** Домашнее устройство (роутер, NAS или ПК в одной сети с камерами) должно быть в сети NetBird и в группе `Home`. Тогда по правилам доступа сервер из группы `remote` сможет подключаться к нему. Группы нужны для сегментации: вы явно разрешаете, кто к кому имеет доступ.

---

## Шаг 5. Настройка правил доступа

Перейдите:

```
Access Control → Policies
```

Нажмите `Add policy` и создайте правило:

Source:

```
remote
```

Destination:

```
Home
```

Protocol:

```
ALL
```

**Зачем:** Без политик NetBird запрещает трафик между устройствами, но при создании аккаунта автоматически появляется политика `Default`: она разрешает всем устройствам связь со всеми. Наше правило говорит: «устройства из группы `remote` (облачный сервер) могут подключаться к устройствам из группы `Home`». Поля Action в политике нет: NetBird умеет только разрешающие правила, всё остальное запрещено. Реально ограничивать доступ правило начнёт, только когда вы удалите `Default`; после этого без него ping до домашнего устройства не пройдёт.

### Доступ к самим камерам через Networks

Политика `remote → Home` открывает доступ только к самому домашнему устройству по его NetBird IP, но не сквозь него. Камеры сидят в домашней подсети со своими локальными адресами и NetBird не запускают, поэтому до них нужен маршрут: в NetBird это делается через раздел Networks, а домашнее устройство становится routing peer.

Перейдите:

```
Networks
```

Добавьте Network:

```
home
```

Через `Add Resource` добавьте ресурс: адрес подсети камер (или адреса отдельных камер с маской `/32`) и группу ресурса:

```
Address: 192.168.1.0/24
Groups: cameras
```

Создайте политику доступа к ресурсу:

```
Source: remote
Destination: cameras
Protocol: TCP
Ports: 554
```

И назначьте домашнее устройство routing peer этого Network.

**Зачем:** Ресурсы Networks не входят в группу `All`, поэтому даже с политикой `Default` до камер без отдельного правила не достучаться. Routing peer по умолчанию делает masquerade — подменяет адрес источника на свой локальный, так что на роутере и камерах ничего настраивать не нужно. На Linux клиент NetBird сам включает IP forwarding. Порт `554` — стандартный для RTSP; если у ваших камер другой, укажите его.

## Шаг 6. Проверка соединения

Получите NetBird IP домашнего устройства:

Пример:

```
100.64.0.5
```

С сервера:

```bash
ping 100.64.0.5
```

Проверьте, что сервер видит Network и достаёт до RTSP-порта камеры (подставьте локальный IP своей камеры):

```bash
netbird networks ls
nc -zv 192.168.1.10 554
```

Если всё работает — сеть настроена.

**Зачем:** Так мы убеждаемся, что VPN работает и сервер в облаке достаёт до домашней сети. Ping проверяет туннель до домашнего устройства, а `nc` — что маршрут через routing peer пропускает RTSP до камеры. Если порт открыт, Frigate сможет забирать потоки по локальным адресам камер.

## Часть 2. Подключение и монтирование диска

**Зачем отдельный диск:** Системный диск (vda) у виртуалки обычно небольшой — этого мало для видеозаписей. В режиме непрерывной записи Frigate пишет круглосуточно, и место быстро закончится. Отдельный диск (vdb) на 256–512 ГБ даёт место под записи, а сколько их держать — настраивается.

Проверяем диски:

```bash
lsblk
```

Пример:

```
vda 40G
vdb 512G
```

---

## Шаг 7. Форматирование диска

```bash
sudo mkfs.ext4 /dev/vdb
```

**Зачем:** Новый диск приходит «сырым» — без файловой системы. `mkfs.ext4` создаёт на нём ext4 — привычную для Linux файловую систему с журналированием: она нормально переживает сбои и спокойно работает с большими видеофайлами. Важно: форматирование удаляет все данные на диске.

---

## Шаг 8. Монтирование

```bash
sudo mkdir /data
sudo mount /dev/vdb /data
```

**Зачем:** Диск нужно «привязать» к каталогу, чтобы система могла с ним работать. Без монтирования запись в `/data` пойдёт на системный диск. После `mount` всё, что пишется в `/data`, сохраняется на отдельном диске.

Проверка:

```bash
df -h
```

---

## Шаг 9. Автомонтирование

Получаем UUID:

```bash
sudo blkid /dev/vdb
```

Редактируем:

```bash
sudo nano /etc/fstab
```

Добавляем:

```
UUID=YOUR_UUID /data ext4 defaults,nofail 0 2
```

**Зачем:** После перезагрузки диск размонтируется, и Frigate перестанет писать записи. Запись в `/etc/fstab` заставляет систему автоматически монтировать диск при загрузке. UUID используется вместо `/dev/vdb`, потому что имена устройств могут меняться, а UUID диска — постоянный. `nofail` не даёт системе зависнуть при загрузке, если диск временно недоступен.

---

## Шаг 10. Настройка прав

```bash
sudo mkdir -p /data/frigate/{config,media,db}
sudo chown -R skv:skv /data/frigate
```

**Зачем:** Каталог `config` нужен для конфигурации (там же по умолчанию лежит база SQLite), `media` — для видеозаписей, `db` — под базу, если перенести её туда из `config` (об этом ниже). `chown` даёт вашему пользователю права на запись, чтобы не использовать `sudo` при редактировании конфигов.

## Часть 3. Установка Docker

![Docker — платформа контейнеризации](/images/external/docker-logo.png "Docker")

**Зачем Docker:** Frigate поставляется как готовый Docker-образ со всеми зависимостями (Python, FFmpeg, детекторы и т.д.). С Docker не нужно вручную собирать окружение и воевать с конфликтами версий, а обновление сводится к перезапуску контейнера с новым образом.

Обновляем систему:

```bash
sudo apt update
```

Устанавливаем Docker:

```bash
sudo apt install docker.io -y
```

Запускаем:

```bash
sudo systemctl enable docker
sudo systemctl start docker
```

Добавляем пользователя:

```bash
sudo usermod -aG docker skv
newgrp docker
```

Проверка:

```bash
docker ps
```

**Зачем `usermod -aG docker`:** По умолчанию сокет Docker принадлежит root, и остальные пользователи работают с ним только через `sudo`. Добавление пользователя в группу `docker` позволяет запускать Docker без `sudo`. Это удобнее, но не безопаснее: членство в группе `docker` по сути даёт права root на хосте, так что добавляйте туда только тех, кому доверяете как root.

## Часть 4. Установка Docker Compose

```bash
sudo apt install docker-compose-v2 -y
```

Пакет `docker-compose` в репозиториях Ubuntu — это старый Compose v1 с командой `docker-compose` через дефис. Нужен `docker-compose-v2`: он ставит плагин, который вызывается как `docker compose`.

Проверка:

```bash
docker compose version
```

**Зачем Docker Compose:** Вместо длинной команды `docker run` с кучей флагов Compose описывает сервисы в YAML-файле. Проще хранить конфигурацию в репозитории, менять параметры и перезапускать одной командой `docker compose up -d`.

## Часть 5. Установка Frigate

![Frigate — NVR с AI-детекцией объектов](/images/external/frigate-logo.svg "Frigate NVR")

Создаём compose-файл:

```bash
nano /data/frigate/docker-compose.yml
```

```yaml
services:
  frigate:
    container_name: frigate
    image: ghcr.io/blakeblackshear/frigate:stable
    restart: unless-stopped
    stop_grace_period: 30s

    shm_size: "512mb"

    volumes:
      - /data/frigate/config:/config
      - /data/frigate/media:/media/frigate
      - /data/frigate/db:/db
      - /etc/localtime:/etc/localtime:ro
      - type: tmpfs
        target: /tmp/cache
        tmpfs:
          size: 1000000000

    ports:
      - "8971:8971"
      - "8554:8554"
      - "8555:8555/tcp"
      - "8555:8555/udp"

    environment:
      - TZ=Europe/Berlin
```

**Что за что в compose:**
* `stop_grace_period: 30s` — даёт Frigate время корректно остановить все свои службы при остановке контейнера.
* `shm_size: "512mb"` — Frigate хранит декодированные кадры в shared memory для детекции. По документации стандартных 128 МБ хватает на 2 камеры 720p, так что для 2–4 камер 256–512 МБ достаточно; при нехватке будет ошибка «Bus error».
* `volumes` — привязка каталогов: `config` для настроек и базы SQLite (по умолчанию `/config/frigate.db`), `media` для записей и клипов. Каталог `db` Frigate сам не использует: чтобы база лежала там, в конфиге нужно указать `database: path: /db/frigate.db`. `localtime` нужен для корректного времени в логах и метаданных. `tmpfs` на `/tmp/cache` (около 1 ГБ) — кэш в оперативной памяти: сюда Frigate сначала пишет сегменты записей, проверяет их и только потом переносит в `recordings` на диск. Документация рекомендует держать этот каталог в tmpfs.
* `8971` — Web UI и API (с авторизацией). `8554` — RTSP-рестрим для камер. `8555` (TCP и UDP) — WebRTC: живой просмотр с малой задержкой и двусторонняя связь с камерами, которые её поддерживают.
* `TZ` — часовой пояс для корректного отображения времени событий.

## Часть 6. Создание конфигурации Frigate

```bash
nano /data/frigate/config/config.yml
```

```yaml
mqtt:
  enabled: false

record:
  enabled: true
  continuous:
    days: 3

cameras: {}
```

**Зачем такая конфигурация:** Минимальный конфиг для первого запуска. MQTT отключён — он нужен в первую очередь для интеграции с Home Assistant. `record` включает запись, а `continuous.days: 3` хранит непрерывную запись (всё подряд, не только при движении или детекции) 3 дня. Старый вариант `retain: days/mode` в актуальных версиях Frigate заменён на `continuous` и `motion`, а записи тревог и детекций хранятся отдельно через `alerts.retain` и `detections.retain`. `cameras: {}` пустой — камеры добавите позже через Web UI или вручную в конфиг, указав RTSP-путь по локальному адресу камеры, до которого сервер достаёт через Networks (например, `rtsp://192.168.1.10:554/stream1`).

## Часть 7. Запуск

```bash
cd /data/frigate

docker compose up -d
```

Проверка:

```bash
docker ps
```

**Зачем `-d`:** Флаг `-d` (detached) запускает контейнер в фоне. Без него терминал будет занят логами Frigate. Контейнер продолжит работать после закрытия SSH.

## Часть 8. Получение пароля

```bash
docker logs frigate
```

или

```bash
docker logs frigate 2>&1 | grep -i password
```

Логин:

```
admin
```

**Зачем:** При первом запуске Frigate генерирует случайный пароль и выводит его в логи — так Web UI не остаётся открытым для всех подряд. Пароль можно сменить в настройках после входа.

---

## Часть 9. Доступ к Web UI

```
https://SERVER_IP:8971
```

**Зачем:** Web UI — основной интерфейс Frigate: просмотр камер в реальном времени, настройка зон и масок, просмотр событий и записей, добавление камер. По умолчанию Frigate включает на порту 8971 TLS с самоподписанным сертификатом, поэтому открывайте адрес через `https://` и будьте готовы к предупреждению браузера о сертификате. Убедитесь, что в Security Groups Yandex Cloud открыт порт 8971 для вашего IP, иначе доступ извне будет закрыт.

---

## Часть 10. Проверка записи

```bash
ls /data/frigate/media
```

**Зачем:** Убеждаемся, что Frigate пишет на отдельный диск. В `media/recordings` появятся каталоги по камерам и датам. Если камеры ещё не добавлены, каталоги будут пустыми — это нормально. Главное, что путь смонтирован и доступен для записи.

## Структура

```
/data/frigate
 ├── config
 ├── media
 ├── db
 └── docker-compose.yml
```

**Назначение каталогов:** `config` — конфиг и SQLite с событиями; `media` — записи, клипы и экспорты; `db` — пуст, пока вы не перенесёте туда базу через `database.path`; `docker-compose.yml` — описание сервиса для перезапуска и обновлений.

## Готово

Frigate работает в Yandex Cloud, ходит к домашним камерам через NetBird и пишет видео на отдельный диск. Систему можно пускать в работу.
